# tabular-ml-pipeline: кого удерживать при ограниченном бюджете

**Задача.** У оператора есть бюджет на удерживающее предложение (скидку) для части клиентов.
Кого из клиентов выбрать? Модель ранжирует клиентов IBM Telco Customer Churn по риску ухода.
Список берётся сверху, а его длина K выбирается по ожидаемой прибыли кампании.

**Главный результат** (out-of-fold на train, 95% bootstrap-CI):

- **lift@10% = 2.88 [2.71; 3.00]**: в верхних 10% списка уходит 76% клиентов при среднем 26.5%.
  Верхние 20% базы содержат 51% всех ушедших (lift@20% = 2.55 [2.45; 2.66]).
- **Точка работы — верхние 25.8% базы**, прибыль **22.9 у.е. [20.7; 25.0] на клиента базы**
  при допущениях из `configs/train.json`. Кривая прибыли плоская: при K от 25% до 33% прибыль
  меняется меньше чем на 1%.
- **Модель — логистическая регрессия.** CatBoost и RandomForest не лучше значимо: Δlift@10%
  −0.007 [−0.085; +0.072] и −0.003 [−0.093; +0.087], corrected t-test на CV 5×5. Новые признаки
  качество не улучшили.
- Test (1409 клиентов, второй взгляд, см. docs/details.md): lift@10% = 2.89 [2.60; 3.21], прибыль
  21.2 у.е. [16.9; 25.8] на клиента при пороге, выбранном на train. Это согласуется с OOF.

**Главный инсайт про сегменты.** Внутри годовых контрактов модель ранжирует прилично: ROC-AUC
0.71 [0.66; 0.76], lift@10% 2.4 [1.7; 3.0]. Но в этом сегменте уходит только 11% клиентов,
поэтому даже в верхних 10% сегмента уходит около 26%. Это ниже точки безубыточности контакта
(35.5% при принятых допущениях). Поэтому список почти целиком (99.9%) состоит из помесячных
контрактов, и ни один ушедший с годовым или двухлетним контрактом в него не попадает. Это
следствие экономики, а не порога: вероятности откалиброваны внутри каждого сегмента, а
отдельные пороги по сегментам дают +0.8% прибыли, и это оценка сверху. Если клиенты на
годовых контрактах ценнее, нужна отдельная кампания с квотой внутри сегмента и своей
экономикой.

**Ограничения.** Данные — снимок, а не история, поэтому это не прогноз будущего ухода
(подробнее — docs/details.md). Денежные параметры — допущения. Вероятность ухода — не эффект от удержания.
Test-выборку уже видели в первой версии.

## Как это было бы в проде

- Признаки собираются на дату T только из данных, известных на T. Метка — уход в интервале
  (T, T+30 дней]. Валидация out-of-time по месяцам: обучение на срезах до месяца M, проверка
  на M+1. **На этом датасете так сделать нельзя**: в нём нет дат и истории, это один снимок.
- Вероятность ухода — не эффект от удержания. Чтобы знать, кого *выгодно* удерживать, нужен
  A/B-тест предложения (он же измеряет r из расчёта прибыли) и uplift-модель, которая
  ранжирует по приросту вероятности остаться.

Подробнее: [`docs/production.md`](docs/production.md).

  лицензия репозитория Apache-2.0.
- SHA-256: `16320c9c1ec72448db59aa0a26a0b95401046bef5d02fd3aeb906448e3055e91`.
- 7043 клиента, 19 признаков + `customerID` + цель, доля ухода 26.5%. Разбиение train/test

## Установка и запуск

Python 3.11+, CPU. Проверено на Windows 10, Python 3.13.

```bash
python -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\Activate.ps1
pip install -r requirements.txt     # точные версии; диапазоны — в pyproject.toml
```

```bash
python -m churn.download_data       # скачать данные и проверить SHA-256
python train.py                     # выбор модели, калибровка, точка работы, артефакт (~7 мин на 12 CPU)
python -m churn.analysis            # SHAP на OOF, анализ ошибок (после train.py)
python -m churn.ablation            # абляция признаков и VIF (~35 мин, в основном CatBoost)
python train.py --evaluate-test     # то же + одна оценка на test, обращение пишется в журнал
python predict.py --input examples/new_customers.csv --output predictions.csv
```

`train.py` без флага test не трогает. Каждое `--evaluate-test` добавляет запись в
`results/test_access_log.json`, а при повторном обращении выводит предупреждение.
`predict.py` пишет `customerID`, `churn_probability` и `in_retention_list`: 1, если клиент
выше порога точки работы. Порог выбран на train и не гарантирует, что на новой выборке список
уложится в бюджет. С `--budget K` в список попадают не больше K клиентов с наибольшей оценкой
среди тех, кто выше порога. Без `--budget` программа предупреждает, если доля выше порога
больше бюджета из конфигурации обучения.

Тесты и smoke-прогон работают без сети на синтетическом наборе той же схемы:

```bash
python -m churn.synthetic           # data/synthetic/telco_synthetic.csv
python train.py --config configs/smoke.json --evaluate-test   # ~6 с
pytest                              # 4 теста из 77 требуют скачанных данных и без них пропускаются
ruff check .
```

CI (`.github/workflows/ci.yml`) прогоняет то же на ubuntu и windows, а затем `predict.py` на
`examples/new_customers.csv` с сохранённой smoke-моделью. Тест `test_user_scenario_cli` проходит
сценарий пользователя только через команды: синтетические данные → `train.py` → загрузка
артефакта → `predict.py` на новых клиентах → проверка порога и бюджета.
